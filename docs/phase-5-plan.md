# 第五阶段计划：受控诊断验收、可复现实验与答辩封版

## 目标

将第四阶段的可解释诊断从功能交付推进到可复现的课程演示证据，并完成性能、治理和回退演练。保持边缘端只回放、XGBoost 唯一 active 报警源、TCN 永远 shadow；不接入现场控制或生产数据。

## 工作包

1. **端到端证据集**：以 Normal、三类目标异常和低置信度样本完成回放，保存脱敏的 API JSON、页面截图、模型/知识库/解释制品版本与时间戳。
2. **解释与检索评审**：按照 `docs/knowledge-base/README.md` 的清单核查每个案例的同窗口映射、特征摘要、引用覆盖和拒答行为；由课程组人工标注事实性和不确定性表达。
3. **性能与降级演练**：测量诊断页首次加载、诊断请求和历史查询的延迟；分别移除解释制品、降低模型置信度和移除知识条目，确认安全降级为“缺少解释”或拒答，且报警状态不变。诊断记录必须持久化 `evidence_status`（`complete` / `degraded` / `refused`）和不可省略的降级或拒答原因，避免仅靠页面文字推断演练结果。
4. **回归与发布封版**：在项目锁定 Python/Docker 环境运行完整 API、ML 和 Web 回归；复核 `.env`、模型制品与演示素材均未入库。打上答辩用版本标签并保留回退说明。

## 验收标准

- 五个案例均能提供可复现记录；四个有效类别的诊断都有模型窗口和至少一个公开来源，低置信度案例拒答。
- 三种降级演练均不发布 MQTT 控制命令、不修改 `Alarm`/`AlarmState`，并保留审计记录。
- 四个有效类别均有自动化的引用覆盖验证；缺失解释制品明确记录为 `degraded`，低置信度、非 active 或无知识条目明确记录为 `refused`。
- 页面和 API 在课程演示机器上保持可交互；实际测得的延迟和运行环境写入演示记录。
- 完整回归通过且无敏感信息、原始数据或模型制品被提交。
